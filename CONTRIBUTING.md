# Правила роботи з репозиторієм

## Модель гілок

| Гілка | Призначення |
|---|---|
| `main` | Стабільна версія проєкту. Зміни потрапляють лише з `develop` через pull request. |
| `develop` | Інтеграційна гілка для завершених функціональних змін. |
| `feature/<назва>` | Розробка окремої функції або модуля. |
| `bugfix/<назва>` | Виправлення помилки. |
| `hotfix/<назва>` | Термінове виправлення у `main`. |

Приклади: `feature/customers-api`, `feature/orders-module`, `bugfix/health-check`.

## Правила комітів

Використовується формат Conventional Commits:

```text
<type>(<scope>): <короткий опис>
```

Дозволені типи:

| Тип | Призначення |
|---|---|
| `feat` | нова функціональність |
| `fix` | виправлення помилки |
| `docs` | документація |
| `test` | тести |
| `refactor` | переробка коду без зміни поведінки |
| `build` | залежності, Docker, конфігурація збірки |
| `chore` | службові зміни |

Приклади:

```text
feat(customers): додати створення клієнта
fix(errors): повертати 404 для відсутнього клієнта
docs(readme): описати запуск проєкту
```

Вимоги до коміту:

1. Опис у наказовому способі, до 72 символів.
2. Один коміт — одна логічна зміна.
3. У коміті немає секретів, паролів і файлів `.env`.

## Правила pull request

1. Кожна зміна оформлюється окремим pull request із `feature/*` у `develop`.
2. Перед створенням PR гілка синхронізується з `develop`.
3. Заповнюється шаблон PR: що змінено, як перевірено, пов’язані завдання.
4. PR проходить перевірку лінтером і тестами.
5. Потрібне щонайменше одне схвалення рев’ю.
6. Злиття виконується через merge commit, після чого гілка видаляється.
7. Прямі коміти в `main` і `develop` заборонені.

## Стиль коду

- PEP 8, довжина рядка до 100 символів.
- Перевірка: `ruff check .`.
- Нові функції супроводжуються тестами `pytest`.
- Публічні функції мають docstring.
