# План підтримки та оновлень CRM System

Документ описує, як підтримується проєкт після релізу 1.0.0: як збирається
зворотний зв’язок, як виправляються помилки, як плануються оновлення та як
перевіряється стабільність системи.

## 1. Канали зворотного зв’язку

Основний канал — **GitHub Issues** репозиторію
`romchikviper-prog/crm-system`. Для звернень використовуються такі типи:

| Тип | Мітка | Призначення |
|---|---|---|
| Помилка | `bug` | Відтворюваний дефект у релізі |
| Покращення | `enhancement` | Нова можливість або зміна поведінки |
| Питання | `question` | Уточнення щодо використання або розгортання |
| Документація | `documentation` | Неточність або прогалина в документації |

Шаблон звернення про помилку містить:

- версію (`1.0.0`) і середовище (Docker, локальний запуск, ОС);
- кроки відтворення;
- очікуваний і фактичний результат;
- логи API та `request_id` із заголовка `X-Request-ID`;
- за потреби — конфігурацію без секретів.

Питання безпеки не публікуються у відкритих Issues: про них повідомляють
власнику репозиторію приватним каналом.

## 2. Класифікація дефектів і строки реакції

| Рівень | Критерій | Приклади | Реакція | Виправлення |
|---|---|---|---|---|
| S1 — критичний | Втрата даних, недоступність API, уразливість | Падіння API, пошкодження бази, відкритий доступ до персональних даних | до 24 годин | 1–3 дні, позачерговий patch-реліз |
| S2 — високий | Не працює основний сценарій, обхідного шляху немає | Не створюється клієнт, health повертає `error` | до 3 днів | до 7 днів, найближчий реліз |
| S3 — середній | Часткова помилка або незручність | Некоректне повідомлення, проблема з пагінацією | до 7 днів | наступний плановий реліз |
| S4 — низький | Косметика, покращення, документація | Друкарська помилка, пропозиція функції | до 14 днів | за пріоритетом у backlog |

Строки є цільовими для навчального проєкту з одним супровідником. Для
кожного звернення фіксується власник, пріоритет і статус.

## 3. Процес виправлення помилки

1. **Відтворення.** Перевірити дефект на тезі `v1.0.0` або актуальній
   гілці `main`, зафіксувати середовище та `request_id`.
2. **Регресійний тест.** Додати тест pytest або сценарій Postman, який
   відтворює помилку й падає до виправлення.
3. **Виправлення.** Виконати зміну в окремій гілці `fix/<опис>` від
   `develop`; не змішувати виправлення з новими функціями.
4. **Перевірка.** Локально виконати `ruff check .`,
   `ruff format --check .`, `pytest` і за потреби Newman; переконатися, що
   CI зелений.
5. **Рев’ю та злиття.** Створити pull request із посиланням на Issue,
   описати причину та спосіб перевірки; злити після схвалення.
6. **Реліз.** Для виправлення випустити patch-версію `1.0.x`, оновити
   `CHANGELOG.md`, створити тег і GitHub Release.
7. **Перевірка після релізу.** Перевірити `/api/v1/health`, виконати
   smoke-сценарії Newman і переглянути логи.
8. **Закриття.** Закрити Issue з посиланням на реліз і тест, який
   підтверджує виправлення.

## 4. План оновлень

### 4.1. Версіонування

Використовується Semantic Versioning у форматі `MAJOR.MINOR.PATCH`:

- `MAJOR` — несумісні зміни контрактів API або схеми даних;
- `MINOR` — нова сумісна функціональність;
- `PATCH` — виправлення помилок і безпеки без зміни контрактів.

Кожна версія отримує анотований тег `vX.Y.Z` і запис у `CHANGELOG.md`.

### 4.2. Регулярність

- patch-релізи — у міру потреби, після виправлення дефектів S1–S2;
- minor-релізи — раз на 1–2 місяці після завершення чергового модуля;
- major-реліз — після зміни публічного контракту API або схеми даних.

Позаплановий реліз випускається для критичних дефектів і питань безпеки.

### 4.3. Гілки та релізний цикл

- `feature/*` і `fix/*` — окремі зміни від `develop`;
- `develop` — інтеграційна гілка;
- `release/vX.Y.Z` — підготовка релізу;
- `main` — стабільна версія та теги.

Зміни проходять pull request і автоматичні перевірки. Прямі коміти в
`main` і `develop` заборонені правилами репозиторію.

### 4.4. Регресійне тестування

Обов’язковий набір перед кожним релізом:

| Перевірка | Команда або засіб | Критерій |
|---|---|---|
| Стиль і форматування | `ruff check .`, `ruff format --check .` | 0 порушень |
| Модульні та інтеграційні тести | `pytest --cov=app --cov-fail-under=80` | 100% тестів, покриття ≥ 80% |
| Контракти API | Newman, 10 ітерацій | 0 failed assertions |
| Інтеграція з PostgreSQL | CI job «Інтеграція» | `database: ok` |
| Збірка образу | CI job «Збірка» | Образ створено |
| Публікація | CD workflow | Образ доступний у GHCR |

### 4.5. Чек-лист релізу

1. Усі Issues відповідного milestone закриті або перенесені.
2. `CHANGELOG.md` містить опис змін.
3. Версія узгоджена в `pyproject.toml`, `app/__init__.py`,
   `app/core/config.py` і README.
4. CI на `main` зелений.
5. Створено тег `vX.Y.Z` і GitHub Release.
6. CD опублікував образ із тегами `X.Y.Z`, `latest`, `sha-<commit>`.
7. Перевірено `/api/v1/health` на розгорнутому образі.
8. Оновлено документацію та посилання на реліз.

### 4.6. Застарівання та сумісність

Несумісні зміни оголошуються в `CHANGELOG.md` і release notes не пізніше
ніж за один minor-реліз. Застарілий маршрут або поле зберігається протягом
одного minor-циклу, після чого видаляється в наступному major-релізі.
Підтримуються останній major-реліз і критичні виправлення для попереднього
minor-релізу протягом трьох місяців.

## 5. Моніторинг і логування

У релізі 1.0.0 реалізовано базовий моніторинг без зовнішніх сервісів:

- **Журнали.** API пише структуровані рядки в stdout: дата, рівень,
  журнал, метод, шлях, код відповіді, тривалість і `request_id`.
- **Ідентифікатор запиту.** Кожна відповідь містить `X-Request-ID`, тому
  скаргу користувача можна зіставити з конкретним записом у журналі.
- **Health-check.** `GET /api/v1/health` перевіряє API та виконання
  `SELECT 1` у PostgreSQL.
- **Стан CI/CD.** GitHub Actions показує результат останньої перевірки та
  публікації; невдалий запуск є сигналом про регресію.
- **Перегляд журналів.** `docker logs -f crm-api`; пошук за
  `request_id` або кодом відповіді.

Мінімальні показники для контролю:

| Показник | Цільове значення |
|---|---|
| Доступність `/api/v1/health` | `status: ok`, `database: ok` |
| Частка відповідей 5xx | < 1% |
| p95 часу відповіді | ≤ 500 мс |
| Успішність CI на `main` | 100% |

Зовнішні сервіси Sentry або LogRocket у 1.0.0 не підключені. Їх доцільно
додати після появи постійного хостингу та публічного доступу; до того
достатньо журналів контейнера, health-check і перевірки доступності
зовнішнім uptime-монітором.

## 6. Межі підтримки

Реліз 1.0.0 є навчальним публічним релізом. Підтримка надається за
принципом best-effort, без гарантованого часу реакції 24/7. У релізі
відсутні автентифікація, пагінація та повний CRUD; ці обмеження
відстежуються в GitHub Issues і враховуються під час планування наступних
версій.
